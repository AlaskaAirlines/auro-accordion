# AB#1372709

## Executive Summary

Accordions are collapsible sections used throughout the guest experience. Applications sometimes need to send a guest straight to one — for example, jumping to a specific section after an action, or moving the guest's attention to the right place for a keyboard or screen-reader user. The standard way to do that in a browser is to "focus" the element in code.

Until now, focusing an accordion in code did **nothing** — the guest's keyboard focus never moved, so the hand-off silently failed. This change makes focusing an accordion behave like focusing any other interactive control: focus lands on the accordion's header (the part you click to open and close it). The result is predictable navigation and a real accessibility improvement for keyboard and assistive-technology users.

Ticket: [AB#1372709](https://itsals.visualstudio.com/E_Retain_Content/_workitems/edit/1372709) — *"Handle programmatic focus() by moving focus to the accordion trigger"* (Bug, Priority 3, Effort — Low).

## The Problem

When code asked an accordion to take focus, the browser did nothing at all. There was no error and no movement — focus simply stayed wherever it already was. For a sighted mouse user this is invisible, but for a keyboard or screen-reader user it's a dead end: the app believes it has moved the guest to the accordion, while in reality the guest was never taken there. Because accordions appear across the guest experience, this made "send the guest to this section" flows quietly unreliable and created an accessibility barrier.

## Root Cause

`AuroAccordion` (`src/auro-accordion.js`) is a `LitElement` that already opts into native focus delegation:

```js
static shadowRootOptions = {
  ...LitElement.shadowRootOptions,
  delegatesFocus: true,
};
```

`delegatesFocus` is real, but it only reaches **one shadow boundary deep**: calling `.focus()` on the host forwards focus to the first focusable element found *directly inside the accordion's own shadow root*. That first element is the trigger, rendered as a nested **custom element**, `<auro-accordion-button id="accordionTrigger">` (`src/auro-accordion.js` `render()`):

```js
<${this.buttonTag}
  ...
  id="accordionTrigger"
  part="trigger">
```

`auro-accordion-button` is **not itself a focusable area** — its host has no `tabindex`, and its own shadow root does **not** set `delegatesFocus`. The genuinely focusable native `<button>` lives one level deeper still, inside the button's shadow root (`AuroAccordionButton` extends `AuroButton`, which renders the real `<button>`). Native focus delegation does not pierce that second boundary, so the browser walks into the accordion's shadow root, finds a custom element with nothing focusable to hand off to, and gives up. `accordion.focus()` therefore resolved to a no-op.

In short: **`delegatesFocus` crosses exactly one shadow root, but the focus target sat two shadow roots down.**

## The Fix

Give `AuroAccordion` its own public `focus()` that explicitly forwards to the trigger (`src/auro-accordion.js`):

```js
/**
 * Moves keyboard focus to the accordion's trigger (the header that expands/collapses the accordion).
 */
focus() {
  this.shadowRoot?.querySelector("#accordionTrigger")?.focus();
}
```

`#accordionTrigger` is the `auro-accordion-button`. It inherits `AuroButton.focus()` — `this.renderRoot.querySelector("button").focus()` — which focuses the real native `<button>` in its shadow root. So the override completes the chain the browser couldn't: **host → `auro-accordion-button` → native `<button>`.**

The optional chaining on `this.shadowRoot?.` (added during the PR #234 code review) guards the case where `focus()` is called before the shadow root exists — e.g. a framework ref callback firing between element connection and Lit's first render. Without it, `this.shadowRoot.querySelector(...)` would throw a `TypeError`; native `HTMLElement.focus()` never throws, so the override matches that contract by degrading to a no-op.

`delegatesFocus: true` is intentionally left in place — it still governs `autofocus`, `:focus`/`:focus-visible` styling on the host, and click-to-delegate behavior; only the programmatic `.focus()` path needed the explicit forward.

Three tests pin the behavior (`test/auro-accordion.test.js`):

| Test | Asserts |
|---|---|
| `focus() moves focus to the trigger button` | Before `el.focus()`, `el.shadowRoot.activeElement` is `null`; after, it is the `.trigger` (`auro-accordion-button`) **and** `trigger.shadowRoot.activeElement` is the native `<button>`. |
| `focus() does not move focus when disabled` | On a `disabled` accordion, `el.focus()` leaves `el.shadowRoot.activeElement` `null` — a disabled trigger stays unfocusable. |
| `focus() does not throw before the shadow root exists` | On a freshly `document.createElement`'d accordion (`shadowRoot` still `null`), `el.focus()` does not throw — the regression anchor for the `this.shadowRoot?.` guard. |

The generated API docs (`docs/api.md`) now list `focus` in the Methods table, produced from the method's JSDoc via the doc build.

## Why This Works

- **It forwards to a target that is itself a focus delegate.** `auro-accordion-button` already knows how to focus its inner `<button>` via the inherited `AuroButton.focus()`. The accordion only needed to reach the button *host*; the button handles the last hop. This mirrors the established Auro pattern rather than inventing a new one.
- **The regression is anchored, not incidental.** The positive test asserts `el.shadowRoot.activeElement` is non-null and is the trigger. Before the fix that value is `null`, so removing the `focus()` method fails the suite — the test measures the exact thing that was broken.
- **Disabled stays correct for free.** When `disabled`, the inner `<button>` carries the `disabled` attribute, so `button.focus()` is a native no-op. No special-casing is needed, and the second test documents that a disabled accordion is intentionally not focusable — consistent with how native disabled controls behave.
- **Rejected alternative — rely on `delegatesFocus` alone.** This is what the component already did, and it cannot work here: delegation stops at the first custom element, which is not a focusable area. Nesting depth, not configuration, is the blocker.
- **Rejected alternative — add `delegatesFocus` to `AuroButton`.** That would make the button host a delegate and might let the accordion's delegation chain through, but it lives in a different package and would change focus semantics for *every* Auro button. Wrong altitude for an accordion-scoped bug; the localized `focus()` override is the correct blast radius.
- **The override honors the native `focus()` contract — it never throws.** Optional chaining on `this.shadowRoot?.` (from the PR #234 review) keeps a too-early call (before first render) a safe no-op, matching `HTMLElement.focus()`. A public method that stands in for a native one shouldn't introduce a throw the native version doesn't have.

## Outcome

Focusing an accordion in code now does what everyone already assumed it did: keyboard focus moves to the accordion's header. Flows that send a guest to a section — after an action, or when jumping to content — work reliably, and keyboard and screen-reader users are actually taken where the app intends. The change is additive and behavior-preserving everywhere else: nothing about opening, closing, styling, or mouse interaction changed, and disabled accordions correctly remain non-focusable. The full accordion test suite passes. (The ticket's cross-browser and Playwright acceptance items are not applicable to this WTR-only standalone component — see Ticket Completeness.)

## Learnings

- **`delegatesFocus` crosses one shadow boundary, not all of them.** If the intended focus target is nested inside another custom element's shadow root, host-level `delegatesFocus` will not reach it. When the trigger is itself a web component, forward focus explicitly.
- **When you can't delegate, forward to something that can.** The clean fix wasn't to reach the deep `<button>` directly, but to call `.focus()` on the intermediate component that already delegates to it. Compose focus hand-offs boundary by boundary.
- **A silent no-op needs a test that measures the boundary it crosses.** Observe focus with `shadowRoot.activeElement` at each shadow root rather than `document.activeElement` (which only ever reports the outermost host). The `null → trigger → button` assertions are what make the regression detectable.
- **Keep the blast radius on the component that has the bug.** Fixing this inside `AuroAccordion` — instead of changing `AuroButton`'s focus semantics for every consumer — kept the change safe and reviewable.
- **Leave working focus affordances alone.** `delegatesFocus` still earns its keep for `autofocus`, `:focus-visible`, and click delegation; the fix adds the missing programmatic path without removing the behavior that already worked.
- **Read the AC against the repo's actual toolchain.** These ADO tickets are generated from a template that appends "Playwright interaction tests" and "cross-browser" boilerplate regardless of target. Standalone Auro components are WTR-only (no Playwright / E2E harness — that lives in `auro-formkit` and the app repos), so those items are *not applicable* here, not skipped work. Score AC items against what the repo can actually do, and flag template mismatches rather than reporting them as plain gaps.
