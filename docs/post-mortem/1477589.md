# AB#1477589

## Executive Summary

Accordions let a page show or hide sections of content. When a person clicks an accordion, a screen reader tells them it opened or closed. But when the **page's own code** opens or closes an accordion automatically — for example, expanding a section after the guest takes an action — screen readers said nothing. A guest relying on a screen reader was left unaware that new content had appeared or disappeared.

This change makes those automatic open/close changes speak up: whenever an accordion's state is changed by code, screen reader users now hear "Expanded" or "Collapsed." Manual clicks are unchanged and are still announced exactly once. The result closes an accessibility gap for keyboard and screen-reader users across every experience that uses accordions.

Ticket: [AB#1477589](https://itsals.visualstudio.com/E_Retain_Content/_workitems/edit/1477589) — *"Announce expanded state to screen readers when auro-accordion is expanded programmatically"* (Bug, Priority 3, Effort — Medium).

## The Problem

Screen readers only announce a change they can perceive. When a guest clicks an accordion header, the header (a button) is focused, and the screen reader speaks its new "expanded"/"collapsed" state as part of that interaction. But when code opens or closes the accordion on its own — no click, no focus change — nothing draws the screen reader's attention, so the change happens in silence. The guest doesn't know content just appeared or vanished, which is a barrier to using the page and an accessibility gap in the design system.

## Root Cause

The trigger's accessible state lives on the `aria-expanded` attribute of the underlying `<button>`. `AuroAccordion.updated()` (`src/auro-accordion.js`) already kept that attribute in sync on every `expanded` change (both click and programmatic), and the button's focused-state change is what a screen reader voices on a manual activation.

The gap: a screen reader only re-announces an element's `aria-expanded` when that element **has focus**. A programmatic change — `el.expanded = true`, a programmatic `toggle()`, or `auro-accordion-group`'s auto-close of sibling panels (`src/auro-accordion-group.js` `handleToggleExpanded()`, which sets `item.expanded = false` on other items) — mutates state without moving focus. The attribute updated correctly, but with focus elsewhere nothing prompted the screen reader to speak. There was no focus-independent announcement channel (an `aria-live` region), so any not-focused state change was silent by construction.

## The Fix

Add a focus-independent announcement channel and drive it from the state change the component already tracks.

- **A visually-hidden live region** in the shadow template (`src/auro-accordion.js` `render()`), placed inside `.componentWrapper` but **outside** the `inert` content `<div>` (an `inert` subtree is removed from the accessibility tree, so a live region inside it would never announce):
  ```html
  <div class="srAnnouncer" aria-live="polite" aria-atomic="true"></div>
  ```
  It has no Lit-bound text, so re-renders never overwrite the text set imperatively.

- **Populate it from `updated()`**, extending the existing `expanded` block that already sets `button.ariaExpanded`:
  ```js
  const isInitialRender = changedProperties.get("expanded") === undefined;
  const triggerFocused = button && this.shadowRoot.activeElement === button;
  if (!isInitialRender && !triggerFocused) {
    const announcer = this.shadowRoot.querySelector(".srAnnouncer");
    if (announcer) {
      announcer.textContent = this.expanded ? "Expanded" : "Collapsed";
    }
  }
  ```

- **A visually-hidden style** for `.srAnnouncer` (`src/styles/style.scss`) using the well-known sr-only recipe (mirroring webcorestylesheets `util_displayHiddenVisually`): absolutely positioned, clipped to a 1px box, no padding/border — off-screen visually but present in the accessibility tree.

Tests (`test/auro-accordion.test.js`) cover a programmatic expand announcing "Expanded", a programmatic collapse announcing "Collapsed", and a user-activated toggle leaving the live region silent.

## Why This Works

- **`updated()` is the one place every state change converges.** Click, direct `expanded=` set, programmatic `toggle()`, and group auto-close all mutate the reactive `expanded` property, so a single hook covers every path without special-casing callers.
- **The focus guard prevents double-speak.** `this.shadowRoot.activeElement === button` is true exactly when the guest just activated this trigger — the case the browser/AT already announces. Announcing via the live region only when the trigger is **not** focused means manual activations stay single-announced while programmatic and group-driven changes get the announcement they were missing. This was the explicit design choice for the fix.
- **The initial-render guard keeps page load quiet.** On the first update the previous `expanded` value is `undefined`; skipping that case avoids announcing state on load.
- **Alternating text guarantees re-announcement.** Because state toggles between "Expanded" and "Collapsed", each change writes new text, which a live region reliably re-reads (identical consecutive text would not re-announce — not a concern here).
- **Placement respects `inert`.** Keeping the live region outside the `inert` content subtree is essential; inside it, the announcement would be suppressed along with the collapsed content.
- **Rejected alternative — announce on every change.** Simpler and more uniform, but it double-announces manual clicks (focused button + live region) and turns group auto-close into a burst of extra "Collapsed" announcements. The focus-guarded approach was chosen instead.

## Outcome

Automatic (code-driven) accordion open/close changes are now spoken to screen reader users — "Expanded" when content appears, "Collapsed" when it hides — including when opening one panel in a group auto-closes another. Manual clicks are unchanged and announced exactly once. The change is additive and behavior-preserving: nothing about visuals, mouse interaction, or the expand/collapse mechanics changed, and there is no announcement on page load. The full accordion test suite passes — though WTR asserts the announcement *text*, not a real screen reader speaking it, so manual VoiceOver/other-pair verification is still worth doing. (The ticket's Playwright acceptance item is not applicable to this WTR-only standalone component — see Ticket Completeness.)

The remaining 1 — **Playwright interaction tests** — is **not applicable to this repo's toolchain**: `auro-accordion` is a standalone, WTR-only component with no Playwright harness (Playwright exists in `auro-formkit` and the app repos, but not in any standalone Auro component). It describes net-new test infrastructure, not work skipped in this fix.

**Resolved**

- **Expanding/collapsing programmatically causes a screen reader to announce the new state.** A visually-hidden `aria-live="polite"` region is populated with "Expanded"/"Collapsed" from `updated()` whenever `expanded` changes without the trigger being focused; asserted by the programmatic expand/collapse WTR tests.
- **Direct user activation still conveys state and is not double-announced.** The focus guard suppresses the live region when the trigger is focused, so a manual click/keyboard activation is announced once (by the focused button's `aria-expanded`, still kept in sync); asserted by the "does not announce when the user activates the trigger" test.
- **WTR unit tests covering the programmatic announcement are added and pass.** Three tests: announces "Expanded", announces "Collapsed", and stays silent on user activation.

**Partial**

- **Verified with VoiceOver on macOS Chrome plus one other screen reader / browser pair.** The announcement *mechanism* is unit-tested (the live region receives the right text), but no manual verification with real screen readers was performed, on any pair. This is feasible without new tooling — just run the screen readers — so it remains a real, open gap.
- **Accordions toggled inside an `auro-accordion-group` announce correctly with no regression.** The group auto-close path flows through the same `updated()` hook (a not-focused sibling collapse announces "Collapsed"), and the existing group test suite still passes, but no test explicitly asserts a *grouped* accordion announces on auto-close.

**Not applicable to this repo's toolchain**

- **Playwright interaction tests for the announcement behavior are added and pass.** There is no Playwright setup in `auro-accordion` (or any standalone Auro component); adding it would be net-new infrastructure beyond this fix.

**Suggested follow-ups:** manual VoiceOver/Chrome (macOS) + a second SR/browser pair (e.g. NVDA/Firefox) verification; and a WTR test for announcement on group auto-close. Standing up Playwright for standalone components is a separate infrastructure decision, not part of this ticket.

## Learnings

- **`aria-expanded` alone only announces when the element is focused.** For state that can change without focus (programmatic updates, sibling auto-close), you need a focus-independent channel — an `aria-live` region — or the change is silent.
- **Announce based on focus, not on the caller.** Using `shadowRoot.activeElement` to detect "the user just did this" cleanly separates the already-announced manual path from the silent programmatic path, avoiding double-speak without threading intent through every call site.
- **Keep live regions out of `inert` (and hidden) subtrees.** An `inert` container is removed from the accessibility tree; a live region nested in it will never fire. Position the announcer as a sibling of the collapsible content.
- **Guard the initial render.** Lit's first `updated()` reports the property as changed-from-`undefined`; treat that as "no announcement" so components don't speak on page load.
- **Don't expose internal a11y helpers as public API.** The visually-hidden announcer is an implementation detail; it should not be a documented, consumer-styleable CSS part.
- **A unit test that sets live-region text is not a screen-reader test.** Asserting `textContent === "Expanded"` proves the mechanism, not that VoiceOver/NVDA actually speak it. Accessibility acceptance that names specific SR/browser pairs needs manual (or automated AT) verification on those pairs — don't let a green WTR run stand in for it.
- **Read the AC against the repo's actual toolchain.** These ADO tickets are generated from a template that appends "Playwright interaction tests" boilerplate regardless of target. Standalone Auro components are WTR-only (no Playwright / E2E harness — that lives in `auro-formkit` and the app repos), so that item is *not applicable* here, not skipped work. Distinguish "infeasible without new infrastructure" (Playwright) from "doable but not done" (manual SR verification, a grouped-accordion test).

## Iterations That Didn't Work

- **Exposing the announcer as a CSS Shadow Part (`part="srAnnouncer"`).** Initially the live region was given a `part` so it would surface in the generated docs. It was removed: a permanently-invisible internal aria-live helper has no meaningful styling use case for consumers, and exposing it would add public API surface (and a documented part) with no purpose. The announcer is now class-only and internal.
