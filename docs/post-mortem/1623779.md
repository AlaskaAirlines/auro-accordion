# Post-Mortem: Janky right-aligned open/close animation (AB#1623779)

**Issue:** AB#1623779

## Reference documents
- Work item — [AB#1623779](https://dev.azure.com/itsals/E_Retain_Content/_workitems/edit/1623779)
- Fix PR — [#234](https://github.com/AlaskaAirlines/auro-accordion/pull/234)

## Summary

With `alignRight` set, the accordion's expand/collapse animation was visibly janky and slow — the
content height stuttered on open and close. The same animation was smooth in the default (left-aligned)
layout. The fix was CSS-only: stop turning `.componentWrapper` into a flex column for right alignment and
instead right-align the trigger on its own with `margin-left: auto`, leaving the wrapper a normal block so
the content height animates on the same path as the default layout.

## Root cause

The height transition relies on `interpolate-size: allow-keywords` (set on `:host`), which lets
`.content` animate between `height: 0` and `height: auto`. The prior `alignRight` rule made
`.componentWrapper` a flex column:

```scss
:host([alignRight]) {
  .componentWrapper {
    display: flex;
    flex-direction: column;
    align-items: flex-end;
  }
}
```

That turned `.content` into a **flex item**. Interpolating a flex item's `height` to/from `auto` forces the
flex layout algorithm to re-resolve the item's size every frame, which is what produced the janky/slow
animation seen *only* when right-aligned. In the default layout `.content` is a normal block, so the
height interpolation runs on the browser's cheap block path and stays smooth.

## Fix

Keep `.componentWrapper` a normal block and handle alignment on the trigger itself:

```scss
:host([alignRight]) {
  .trigger {
    display: block;
    width: fit-content;
    margin-left: auto;
  }
}
```

A block `.trigger` sized to `fit-content` and pushed right with `margin-left: auto` achieves the same
visual right-alignment without making `.content` a flex item — so the content height animates on the same
smooth path as the default layout.

## Why the flex approach was the wrong tool

Flex was only ever used here to push a single child to one edge — a job `margin-left: auto` does on a block
element without changing the formatting context of siblings. The flex container had the side effect of
re-typing `.content` as a flex item, and that side effect (not the alignment itself) was the bug. Removing
the flex context removed the per-frame resize cost while preserving the alignment.

## How it was caught

Reported as a visible animation-quality regression scoped to the right-aligned configuration — the open/close
felt slow and stuttery with `alignRight`, but not in the default layout. That "only when right-aligned"
asymmetry pointed directly at the `alignRight`-specific flex rule as the differentiator.

## Verification

- **Manual** — open/close animation confirmed smooth with `alignRight` set, matching the default layout;
  trigger remains right-aligned. Checked alongside `chevron="right"` and grouped configurations, which share
  the wrapper.
- **Build** — `npm run build` succeeds; `docs/api.md` regenerates.
- **Automated animation coverage** — none. The jank was a rendering/timing characteristic, not a
  computed-style assertion, so it is not meaningfully unit-testable at the WTR level. Consistent with the
  outstanding VRT gap noted in the AB#1536514 post-mortem (Recommendation #5), animation smoothness relies on
  manual/visual check until VRT tooling exists.

## What went right

- **The asymmetry localized the bug immediately.** "Smooth by default, janky only when right-aligned" made the
  `alignRight` flex rule the obvious suspect and avoided a broad hunt through the transition code.
- **The fix removed a formatting-context side effect rather than fighting it.** Swapping flex for
  `margin-left: auto` kept the diff to the one rule that caused the problem.

## What went wrong

- **Flex was used for simple edge-alignment**, silently re-typing `.content` as a flex item and coupling the
  alignment concern to the animation path. The interaction between `interpolate-size` height animation and
  flex item sizing was not anticipated when the right-align layout was first written.

## Recommendations

1. **Prefer margin-based alignment over a flex/grid container when only one child needs to move to an edge** —
   it avoids changing the formatting context (and animation behavior) of siblings.
2. **When animating `height` to/from `auto`, keep the animated element a block-level box.** Flex/grid items
   re-resolve size during the interpolation and can stutter.
3. **Follow-up:** visual-regression coverage for the expand/collapse animation (default and `alignRight`) is
   still outstanding — same repo-wide VRT gap tracked in AB#1536514; baselines should be added wherever Auro's
   VRT runs.
