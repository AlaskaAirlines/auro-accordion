# Post-Mortem: `auro-accordion-group` scrolls the page even when it is already in view (AB#1616757)

**Branch:** `jbaker/restrictScrollintoView`
**Scope:** `handleToggleExpanded()` in `src/auro-accordion-group.js`, plus four new tests in `test/auro-accordion-group.test.js`.

## What happened

When one accordion in a group was expanded, the group called `scrollIntoView()` unconditionally. That was intended for the case where expanding a panel pushes the group partly or wholly off-screen — a helpful "bring the thing you just opened back into view" nudge. But it fired **every** time a panel toggled, including when the group was already fully visible.

The result was a jarring smooth-scroll on interactions that shouldn't have moved the page at all: a user clicks a trigger that's sitting comfortably in the middle of the viewport, and the page slides anyway. On short pages nothing visible happened; on longer pages, or with the group near the top or bottom of the fold, the unwanted scroll was obvious and disorienting.

Concretely, the toggle handler ended with:

```js
this.scrollIntoView({
  behavior: "smooth",
  block: "nearest",
});
```

No condition guarded the call. The behavior was correct only by accident — whenever the group happened to be out of view, the scroll was exactly what you wanted, so the bug hid behind the cases where the feature was doing its job.

## How the first fix was wrong

The obvious fix is "only scroll when the group isn't in view," and that's the right instinct. The first attempt got the *shape* right and the *predicate* wrong.

**First predicate — "fully inside the viewport."**

```js
const rect = this.getBoundingClientRect();
const inView = rect.top >= 0 && rect.bottom <= window.innerHeight;
```

This reads as "in view" only when the entire group fits between the top and bottom of the viewport. That's too strict. A tall group — several panels, or one long expanded panel — is *taller than the viewport by design*, so `rect.bottom <= window.innerHeight` is false even when the user can plainly see the group and its trigger. Under this predicate a partially-visible-but-clearly-on-screen group still scrolls, which is the same annoyance the fix was meant to remove, just in fewer cases.

**Corrected predicate — "any part intersects the viewport."** PR review caught it, and the check became an intersection test:

```js
// Treat the group as "in view" when any part of it intersects the
// viewport so we only scroll when it is entirely above or below the fold.
const rect = this.getBoundingClientRect();
const inView = rect.bottom > 0 && rect.top < window.innerHeight;
```

Now the group is considered in view if any portion overlaps the viewport, so `scrollIntoView()` fires only when the group is *entirely* above (`rect.bottom <= 0`) or *entirely* below (`rect.top >= window.innerHeight`) the fold — the only situations where an automatic scroll is actually helpful.

## Root cause

The specific bug is a symptom. The system produced it for two reasons:

1. **An unconditional side effect where a conditional one was intended.** `scrollIntoView()` is a user-visible, involuntary page movement. Wiring it to "a panel toggled" instead of "a panel toggled *and the group is off-screen*" meant the common case (group already visible) paid for the rare case (group off-screen). Any imperative scroll needs an explicit "should I?" guard; this one had none.

2. **The behavior was never asserted.** There was no test that a toggle *doesn't* move the page, so the unconditional call looked complete. The feature "worked" in the sense that it scrolled — nothing distinguished "scrolled because it needed to" from "scrolled because it always does."

## The fix

`src/auro-accordion-group.js` — guard the scroll behind an intersection-based in-view check inside `handleToggleExpanded()`:

```js
// Treat the group as "in view" when any part of it intersects the
// viewport so we only scroll when it is entirely above or below the fold.
const rect = this.getBoundingClientRect();
const inView = rect.bottom > 0 && rect.top < window.innerHeight;

if (!inView) {
  this.scrollIntoView({
    behavior: "smooth",
    block: "nearest",
  });
}
```

`test/auro-accordion-group.test.js` — four tests pin the behavior across the cases that matter:

| Test | Setup | Asserts |
|---|---|---|
| does not scroll when accordion group is already in view | `getBoundingClientRect` stubbed to an in-viewport rect (`top: 0, bottom: 100`) | `scrollIntoView` is **not** called |
| scrolls into view when accordion group is out of view | `getBoundingClientRect` stubbed to an off-screen rect above the fold (`top: -500, bottom: -400`) | `scrollIntoView` **is** called |
| scrolls into view when accordion group is entirely below the fold | `getBoundingClientRect` stubbed to a rect below the fold (`top: innerHeight + 100, bottom: innerHeight + 500`) | `scrollIntoView` **is** called |
| does not scroll when accordion group is taller than the viewport but partially in view | `getBoundingClientRect` stubbed to a rect that overflows the fold both ways (`top: -500, bottom: innerHeight + 500`) | `scrollIntoView` is **not** called |

The above/below pair exercises both halves of the predicate (`rect.bottom > 0` and `rect.top < window.innerHeight`) so a sign-flip in either one fails the suite rather than silently killing one branch. The taller-than-viewport case is the one that separates the intersection predicate from the rejected containment predicate: `top < 0` and `bottom > innerHeight` at the same time. Containment (`top >= 0 && bottom <= innerHeight`) would score it out-of-view and scroll; intersection correctly leaves the visible group alone. Without it, a regression back to containment logic would pass the suite.

Two hardening details came out of review:

- **Stub the rect, don't rely on layout.** The in-view test originally trusted that "the element is in view by default in the test viewport." That's fragile — the result depends on how tall the expanded content renders. Both tests now stub `getBoundingClientRect` to an explicit rect so they exercise the predicate directly, independent of rendered height.
- **`try`/`finally` around the stubs.** Both tests patch `scrollIntoView` and `getBoundingClientRect` on the element. Restoring them inside a `finally` guarantees the patches don't leak into later tests if an assertion throws.

## Why nothing caught it

- **No test asserted the negative case.** WTR unit tests covered expansion/toggle state, but nothing asserted that toggling a visible group leaves the scroll position alone. A missing assertion, not a failing one.
- **The bug is invisible on the pages tests run on.** In a small test fixture (and on short demo pages) the group is fully in view and `scrollIntoView({ block: "nearest" })` is effectively a no-op, so the defect produced no observable symptom in exactly the environment where it would have been noticed.
- **Correct-by-accident cases masked it.** Whenever the group genuinely was off-screen, the scroll was the desired behavior — so casual testing saw a feature working, not a guard missing.

## Lessons learned

- **An involuntary, user-visible side effect needs an explicit guard.** `scrollIntoView()` moves the page under the user's feet. "Toggled" was the wrong trigger; "toggled and off-screen" was the intent. Reach for the condition before the side effect, not after.
- **"In view" is an intersection test, not a containment test.** `top >= 0 && bottom <= innerHeight` silently means "small enough to fit *and* fully visible," which fails for any element taller than the viewport. When you mean "any part is visible," write `bottom > 0 && top < innerHeight`.
- **Test the negative.** The valuable assertion here is that a visible group *doesn't* scroll. Behavior that is "do nothing in the common case" still needs a test, or it regresses invisibly.
- **Don't let a test depend on rendered layout when you can state the input directly.** Stubbing `getBoundingClientRect` to a fixed rect makes the test about the predicate, not about how tall the content happens to render in the test runner.
- **Restore global/element patches in `finally`.** A thrown assertion mid-test shouldn't leak a patched `scrollIntoView` into the next test.

## Defenses to add (follow-ups)

1. **A shared in-view helper.** If other components imperatively scroll on interaction, factor the intersection predicate into one tested utility rather than re-deriving the rect math per component (and re-making the containment-vs-intersection mistake).
2. **A `prefers-reduced-motion` check.** A smooth auto-scroll should probably respect `prefers-reduced-motion: reduce` — worth confirming the off-screen scroll degrades to an instant jump for users who ask for less motion.
3. **Cross-browser smoke of the scroll path.** The in-view logic is pure `getBoundingClientRect`/`window.innerHeight` math, but the `scrollIntoView({ behavior: "smooth" })` call itself is worth a quick check across the supported browsers.
4. **Measure the rect *after* the expansion renders.** `handleToggleExpanded` reads `getBoundingClientRect()` synchronously inside the `toggleExpanded` listener, but the child accordion sets `this.expanded` and dispatches the event *before* Lit flushes the DOM update — so the guard measures the group's **pre-expansion** layout. If expanding a panel pushes the group below the fold, the pre-render rect still reads as in-view, `inView` is `true`, and no corrective scroll fires. This is pre-existing (the old unconditional `scrollIntoView({ block: "nearest" })` was also a no-op on a pre-expansion in-view element), but the guard makes it a silent no-op instead of an attempted scroll. A correct fix would `await` layout settling (`updateComplete` / `requestAnimationFrame`) before re-checking position, or wire an `IntersectionObserver`.
